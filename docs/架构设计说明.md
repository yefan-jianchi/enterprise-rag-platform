# 架构设计说明

> 这份文档不重复 README 的功能清单，只讲**每个关键决策「为什么这么做」以及代价是什么**。
> 面试被追问设计取舍时，直接照这里答。

---

## 一、整体：为什么是「Java + Python」双层

| 方案 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- |
| 全 Java（Spring AI / LangChain4j） | 一套工程、部署简单 | 文档解析、FAISS、重排生态不如 Python 全；调 Python 侧算法库别扭 | ✗ |
| 全 Python（FastAPI 一把梭） | AI 生态最全 | 企业级权限/事务/多租户/审计要自己造轮子，Java 岗位优势体现不出来 | ✗ |
| **Java 业务层 + Python AI 层**（本项目） | 各自用最擅长的栈；检索（CPU 密集）与业务（IO 密集）可独立扩容 | 多一个服务、多一次跨进程调用（局域网 <5ms，可接受） | ✓ |

**边界怎么划的**（很重要，面试会问）：
- Java 拥有**数据的唯一真相**：租户、用户、权限、知识库、文档元数据、分块正文、会话、审计、成本。
- Python 拥有**算法与索引**：解析、分块、向量化、FAISS/BM25 索引、检索排序。
- Python 侧的 chunk 元数据（正文、页码）是**为检索服务的副本**，不是真相源；
  真要溯源，Java 用 `chunk_id` 回 MySQL 查 `kb_chunk`。
- 好处：Python 服务可以随时重启重建索引，不影响业务数据。

## 二、数据模型的关键设计

### 1. 为什么所有表都带 `tenant_id`
多租户有三种做法：分库、分 schema、**共享表 + 行级过滤**。
中小规模 SaaS 用第三种成本最低。代价是**任何一次查询漏写 tenant_id 就是越权**，
所以我在架构上强制：JWT → 过滤器 → `TenantContext`(ThreadLocal) → 数据访问层统一拼条件，
并在代码评审上把「业务 SQL 必须带租户条件」当成硬规则。

### 2. 为什么 `kb_document.status` 用字符串而不是数字枚举
`PENDING / PARSING / CHUNKING / EMBEDDING / INDEXED / FAILED` ——
用字符串，DBA 直接 `select * from kb_document where status='FAILED'` 就能排查，
日志里也能看懂。数字枚举省的那点空间不值得牺牲可读性。

### 3. 为什么 `kb_chunk` 存 `page_no / char_start / char_end`
这是**引用溯源能不能做成的分水岭**。如果解析时不记录，后面任何环节都补不回来。
`char_start/char_end` 还能支持「高亮原文位置」这种进阶功能。

### 4. 为什么有 `eval_retrieval_case` 这张表
没有评测集的 RAG 项目，效果全靠嘴说。这张表让「命中率提升」变成**可复现的数字**，
也是面试里最能打的一张牌。字段含 `strategy`，可以对比不同策略在同一批问题上的表现。

### 5. 为什么 `ai_call_log` 独立于 `chat_message`
`chat_message` 只记对话；`ai_call_log` 记**所有**模型调用——包括向量化、重排、查询改写。
成本统计必须覆盖全部调用，否则算出来的钱是错的。

## 三、检索链路的设计权衡

### 1. 向量索引：FAISS `IndexIDMap2(IndexFlatIP)`
- **内积 vs L2**：向量已 L2 归一化，内积 == 余弦相似度，用 `IndexFlatIP` 比 `IndexFlatL2` 直观。
- **为什么套 IDMap2**：让 FAISS 直接吃业务库的 `chunk_id`。
  否则 FAISS 只认 0..N-1 的连续下标，删一个文档就要重建全部映射，非常难受。
- **代价**：`IndexFlatIP` 是暴力检索，O(N)。十万级以内毫秒级可用；
  再大要换 `IndexIVFFlat`（需要训练）或上 Milvus。

### 2. BM25：自己实现而不是用库
`rank_bm25` 也能用，但自实现有三个好处：
1. 能自由控制分词（中文必须带**字符二元组**兜底，否则专业术语一多召回就崩）；
2. `k1=1.5 / b=0.75` 可按业务调参；
3. 面试能讲清楚 IDF 加权是怎么算的——**`IDF` 还被重排器复用了**。

### 3. 融合：为什么是 RRF 而不是加权求和
加权求和要先解决「向量分是余弦 0~1、BM25 分是 0~20+ 的无界值」这个量纲问题，
归一化方式（min-max / z-score）本身又会引入新的偏差，且要调权重。
RRF 只看**名次**：`score = Σ 1/(60 + rank)`，天然免疫量纲差异，工程上稳健得多。

### 4. 重排：双层设计
- **有真模型**：Listwise Rerank —— 把候选片段编号丢给模型打 0-10 分，解析 JSON 后重排。
- **没有模型**：`HeuristicReranker` —— 用 BM25 的 IDF 做**加权词重叠**，
  再叠加「整句短语命中加成」和「过短片段惩罚」。
  它不是简单的关键词计数：**稀有词命中权重更高**，这已经逼近交叉编码器的直觉。

### 5. 查询扩展：改写 + HyDE 都要不要默认开
默认开启，但注意两点：
- 每多一路查询就多一次召回 + 一次模型调用（成本翻倍）；
- Mock 模式下的改写质量有限，所以真实收益要在真模型环境评估。
工程上应该做成**按知识库可配**，并在 `ai_call_log` 里能看到改写的成本。

## 四、流式输出（SSE）的设计

### 1. 事件协议
```
event: meta    → {"traceId":"...","citations":[...]}    先给引用，前端先渲染卡片
event: delta   → {"content":"增量文字"}                 逐字追加
event: done    → {"elapsedMs":1234,...}                 收尾 + 统计
event: error   → {"message":"..."}                      异常也要给明确收尾
```
**为什么 meta 要单独一个事件**：引用是检索阶段就确定的，比正文先就绪。
先渲染引用能让用户感觉「秒回」，体验比等正文出来再补引用好得多。

### 2. 为什么用 SseEmitter 而不是 WebFlux
业务侧是标准 Spring MVC + JPA（阻塞式）。为了一个流式接口引入 WebFlux，
会让整个技术栈变成响应式，JPA 在响应式上下文里还要额外处理线程模型，得不偿失。
`SseEmitter` 在 MVC 里足够用，配合线程池即可。

### 3. 必须注意的反代配置
`proxy_buffering off` + `proxy_cache off` + `proxy_read_timeout 300s`，三件套缺一不可。
少了第一个，SSE 会被 Nginx 攒到最后一次性下发，用户看到的是「转圈 20 秒然后全出来」。

## 五、多模型适配层

```
ModelRouter
   ├── 按 ai_model_provider.priority 升序选路
   ├── 调用失败 / 超时 → 自动切下一个提供方（Fallback）
   ├── API Key：环境变量优先，其次数据库密文（AES 解密）
   └── 每次调用写 ai_call_log（tokens + cost_yuan + latency + 成功与否）
```

**为什么能统一**：DeepSeek、通义、OpenAI 都提供 OpenAI 兼容接口，
差异只在 `base_url / api_key / model` 三件事，所以一个 `OpenAICompatLLM` 就能覆盖三家。
真正需要单独适配的是**向量模型**——维度不同（通义 v3=1024，OpenAI small=1536），
所以 `embed_dim` 必须和索引一致，换模型必须重建索引（代码里做了维度校验）。

## 六、降级设计（工程成熟度的体现）

| 缺什么 | 降级方案 | 配置项 |
| --- | --- | --- |
| 没有模型 API Key | 本地 Mock 模型：按 Prompt 语义从上下文挑句组装回答 | `LLM_PROVIDER=mock` |
| 没有向量 API | 本地哈希向量：jieba 分词 + 字符二元组 → crc32 → 384 维 | `EMBED_PROVIDER=mock` |
| 没有 Redis | 内存缓存实现（单机开发够用） | `app.cache.type=memory` |
| 没有 MinIO | 本地文件存储实现，接口不变 | `app.storage.type=local` |
| 没有 Docker | `scripts/dev.ps1` 直接起三个进程 | — |
| Windows 中文路径 | 数据目录自动降级到 `%LOCALAPPDATA%` | `DATA_DIR` |

**为什么值得这么做**：面试官问「你这套东西在我机器上能跑吗」，
答案是「只要有个 MySQL 就能跑，什么都不装也能演示检索与问答全链路」。

## 七、已知限制（主动说出来，比被问出来强）

1. **FAISS 是单机内存索引**，多实例部署时索引不共享 → 要么每实例各自建索引，要么换 Milvus。
2. **文档解析是同步的**（在 Python 内），大文件会占住 worker → 应该改成任务队列。
3. **评测集只有 8 条**，统计意义有限 → 需要扩到 100+ 并引入答案质量评估。
4. **没有做重排序的缓存**，相同问题重复问会重复调用模型 → 可加语义缓存。
5. **权限校验依赖注解**，复杂的数据级权限（比如「只能看自己部门的文档」）还没做。
6. **跨小节的复合问题单块命中率偏低**：
   像「耳机退款多久到账」同时涉及「商品说明」和「售后政策」两个小节，
   任何单块都装不下完整答案，IDF 加权重排会把更稀有的词（耳机）所在块排到前面。
   当前靠 Top-K（Hit@5=100%）兜住；更好的做法是 **MMR 多样性选择**或
   **查询分解（Query Decomposition）**——已列入待完善。

## 八、一个刻意没做的事：不为评测指标调参

评测里有一条 Hit@1 未命中（「耳机退款多久到账」）。本可以调一下 RRF 的 k 值、
或者给 rerank 加个特判把它刷成 100%，但**这是过拟合评测集**：

- 评测集只有 8 条，动一个参数就能翻转 12.5 个百分点，这种「提升」没有泛化意义；
- 真正的问题是**评测设计**：跨小节问题本来就该用 Hit@K 衡量，而不是 Hit@1；
- 正确的改进方向是**扩评测集 + 引入多样性选择**，而不是让算法去迎合 8 条样本。

面试里如果被问「你的指标怎么从 94% 变成 87.5%」（早期粗粒度分块时 Hit@1 更高），正确答案是
**「因为我把分块改成了不跨页，页码精确了，但块粒度变细，跨小节问题更难单块命中——
这是真实取舍，我选择保住引用溯源的准确性，并用 Hit@K 衡量效果」**，
而不是含糊其辞。
