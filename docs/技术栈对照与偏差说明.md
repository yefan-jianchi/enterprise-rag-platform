## 二、Spring AI 是「并存」而不是「替换」（面试会问，这么答）

### 事实
项目里现在有 **4 个 `ChatModel` 实现**，由 `app.ai.engine` 开关与 `provider_code` 共同决定走哪个：

| 实现 | 用途 |
| --- | --- |
| `SpringAiChatModel` | **Spring AI 1.0**（`OpenAiChatModel` / `ChatResponse` / `Usage`），Spring AI 路径 |
| `OpenAiCompatChatModel` | 自研，直接打 OpenAI 兼容协议（DeepSeek/通义/OpenAI） |
| `MockChatModel` | 自研，离线模拟（无 Key 也能跑全链路），**默认引擎** |
| `ModelRouter` | 按 `priority` 选路 + 失败自动 Fallback + 写 `ai_call_log` |

### 为什么默认仍是 legacy（自研）而不是 Spring AI

因为整个项目有一条硬约束：**不填任何 API Key 也要能把 RAG 全链路跑起来**。
`MockChatModel` 是这条约束的实现基础，而它不属于 Spring AI。
所以选择「并存 + 开关切换」，而不是把自研实现删掉换成 Spring AI：

- 默认 legacy → 保证任何人 clone 下来就能跑、测试能在 CI 里离线跑
- 想用 Spring AI → `app.ai.engine=spring-ai`，配好 Key 即可

### 这反而是更好的答案
面试如果问「你为什么用 Spring AI 又自己写一套」，正确答法是：

> 因为我要支持**离线可运行**和**精确成本记账**这两个横切需求。
> Spring AI 的 `ChatClient` 抽象很适合做「连得上模型」的场景，
> 但我需要一个能在没有 Key 时顶上的 Mock 实现，还要在同一处拿到 usage 写审计表。
> 所以我的做法是**把 Spring AI 作为其中一个实现接进来**，
> 用统一接口 + 引擎开关管理，而不是让框架绑死我的架构——
> 这也验证了「面向接口编程」到底有没有用：**加一个 Spring AI 实现，业务代码一行都没改。**

### 升级代价（如实记录）
为了接 Spring AI 1.0（基线是 Spring Boot 3.4.x），把 Spring Boot 从 **3.3.5 升到了 3.4.5**。
升级前先备份了 `pom.xml`，升完必须重跑全链路验收 —— **24/24 全绿才算通过**。

## 四、两个「刻意不用」的决策（面试最容易被追问的两点）

### 4.1 为什么不用 `spring-ai-starter-model-openai`，而用底层 `OpenAiApi` + Builder

starter 的自动配置只面向「**一个应用配一套模型凭据**」：启动时从 `spring.ai.openai.*`
读一组 baseUrl/apiKey/model，构造**一个** Bean。

而本项目是**多租户 + 多提供方**：
- 凭据存在 `ai_model_provider` 表里，**运行期**按租户和 `priority` 决定
- API Key 是 **AES 加密**存储的
- 还要支持「同一进程内同时存在 deepseek / 通义 / openai / mock 四个提供方」

自动配置在这里根本不适用。所以正确做法是用 Spring AI 的底层
`OpenAiApi` + `OpenAiChatModel.Builder` **按需构造实例**（`SpringAiChatModelFactory` 做了缓存）。
**这正是 Spring AI 官方推荐的多模型用法 —— starter 只是把这套 Builder 再包一层而已。**

> 面试价值：这题能区分「会用 starter」和「知道 starter 下面是什么」。
> 能把「为什么自动配置不适用」讲清楚，说明真的读过框架设计。

### 4.2 为什么明确不做 LangChain4j

评估后决定**不做**，三条理由：

1. **能力完全重叠、零增量**。LangChain4j 的两个卖点（LLM 抽象层、AiServices 声明式接口 + Tool Calling 编排）
   项目里都已经覆盖：模型抽象层现在有**两套引擎**（自研 + Spring AI）可切换；
   Tool Calling 的 `CustomerServiceAgent` 已是完整的「模型决定 → 后端执行 → 结果回灌」循环，且跑在 24/24 验收里。
2. **会破坏项目最关键的那条约束**。自研 Tool Calling 走的是「模型输出 JSON → 后端解析执行」，
   对模型能力要求极低，**Mock 模型也能跑**。而 LangChain4j 的 `@Tool` / AiServices 依赖原生
   function-calling 协议（严格 `toolCallId`、返回类型匹配），Mock 模型不支持 ——
   等于在「离线可演示」这条最难验收的路径上加一条框架特有分支。
3. **依赖冲突风险实打实**。LangChain4j 1.x 依赖 OkHttp + Retrofit2，而 MinIO SDK 已经在用 OkHttp，
   版本对齐是典型高风险改动。

> **面试话术**：不要说「LangChain4j 我没用」，要说
> 「我评估过 LangChain4j，结论是不引入 —— 它的能力与我现有的 Spring AI + 自研双层实现重叠，
> 而它依赖的原生 function-calling 协议会让我的离线 Mock 路径失效，风险收益比不划算」。
> **能说出「我为什么不做某件事」，比列出「我用了什么」更能体现判断力。**

## 五、结论

**能写进简历的，必须是代码里真实存在的。** 本项目的真实技术栈是：

> Spring Boot 3.3 + Java 21 + Spring Security(JWT) + JPA · Vue3 + Vite + Element Plus ·
> FastAPI + LangChain 1.4 + FAISS + 自研 BM25/RRF/重排 · MySQL 8 + Redis/MinIO(可切换) ·
> Docker Compose + Nginx · 多模型适配（DeepSeek/通义/OpenAI，含离线 Mock 降级）

比最初的设想少了 Spring AI / LangChain4j / Milvus 三个名词，
但多了一套**能跑起来、有测试、指标可复现、坑都踩过**的系统——
面试里能讲清楚细节，比堆名词有用。

## 七、Spring AI 接入的「可达性证明」（怎么证明一个框架真的被调用）

接完 Spring AI 有个尴尬问题：**默认引擎是 legacy，怎么证明 Spring AI 那段代码真被执行过？**
「能编译」和「Bean 能构造」都不算证据。这里记录一个可复现、不依赖外网、不污染数据的做法。

### 7.1 先说清一个容易搞错的事实

`/api/chat/stream`（对话中心）**根本不走 Java 的 `ChatModel` 层** ——
它把 provider 透传给 Python AI 服务，真正调模型的是 Python。
所以必须走 **`/api/cs/stream`（智能客服，非 mock 模式）** 才能进
`ModelRouter.chatWithFallback → toChatModel` 这条 Java 侧路径。
（第一轮就是测错了接口，白跑一趟——这也是个教训：**验证前先确认代码路径**。）

### 7.2 做法

1. 用一个假 Key 让 `deepseek` 变成 callable：`-DDEEPSEEK_API_KEY=sk-fake-...`
2. 临时把 `ai_model_provider.base_url` 指向本机 AI 服务 `http://localhost:8001/v1`
   （该服务没有 `/chat/completions`，必然 404 —— 这样不依赖外网也不会真花钱）
3. 调 `/api/cs/stream` 并指定 `providerCode=deepseek`
4. 看日志：能证明「Spring AI 被构造 + 请求真的发出了 + 失败后 Fallback 生效」
5. **还原**：base_url 改回官方地址，删掉假 Key，用 SQL 核对 provider 表

### 7.3 决定性日志

```
ModelRouter              - 使用 Spring AI 引擎构造模型: deepseek/deepseek-chat
SpringAiChatModelFactory - [Spring AI] 构造 OpenAiChatModel: provider=deepseek
                           baseUrl=http://localhost:8001/v1 model=deepseek-chat
AiCallLogService         - 模型调用失败已记账: error=404 - {"detail":"Not Found"}
ModelRouter              - 模型调用失败，尝试下一个：deepseek/deepseek-chat
MockChatModel            - [mock] 生成回答 89 字
ModelRouter              - 模型 Fallback 生效：前 1 次失败，最终由 mock/mock-chat 成功
```

**证明力在哪：**
1. `使用 Spring AI 引擎构造模型` 这句日志**只存在于 `ModelRouter` 的 spring-ai 分支**；
2. 错误体 `{"detail":"Not Found"}` 是 **FastAPI 的错误格式**，
   证明请求是经 Spring AI 自己的 `OpenAiApi` HTTP 客户端真打到了 8001；
3. `模式=TOOL_CALLING`（而非 `RULE_INTENT`）证明走的是非 mock 分支；
4. 随后 Fallback 到 mock 成功，说明**异常路径与降级路径都通**。

> **方法论**：证明「某框架真的被用了」，要看**只有该框架才能产生的副作用**
> （它特有的日志、它特有的错误格式、它特有的对象），而不是「代码里有它的 import」。

### 7.4 结果

- jar 从 83.7 MB → **97 MB**，内含 `spring-ai-openai/model/commons/client-chat/retry/template-st` 六个 1.0.0 库
- 新增 2 个类（`SpringAiChatModel` + `SpringAiChatModelFactory`），**零删除**
- 默认引擎仍 `legacy`，离线 Mock 路径**一行未动**
- **回归验收 24/24 全绿**（跑了 3 次）
- 顺带修掉一个真 bug：SSE 的 **ASYNC 二次派发**重跑安全过滤器链会抛
  `AuthorizationDeniedException`（日志刷 `Access Denied ... response is already committed`），
  加 `dispatcherTypeMatchers(ASYNC, ERROR).permitAll()` 后干净

> **回滚方式**：`copy pom.xml.bak pom.xml` + 删掉那 2 个新类 + 重新打包。
> 注意 **`pom.xml.bak` 不能单独编出基线**（新代码还引用 Spring AI 类）——
> 这正是「只新增不替换」的好处：**回滚面收敛到 2 个文件 + 1 个 pom**。
