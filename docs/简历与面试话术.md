## 二、面试怎么讲（STAR）

### 1 分钟版（自我介绍里带一句）

> 我做过一个企业级 RAG 知识库与智能客服平台。它分两层：Java 层管业务和权限，
> Python 层管 RAG 算法。检索这块我没有只调向量库，而是自己实现了 BM25 + FAISS 双路召回，
> 用 RRF 融合再重排，并且做了引用溯源和命中率评测——混合检索把 Top1 命中率从纯向量的 50% 提到了 87.5%，
> Top3 和 Top5 都是 100%，而且我能说清楚这个数字在 8 条小评测集上有多大可信度。
> 部署上用 Docker Compose 编排了 MySQL、Redis、MinIO、前后端一共七个容器，Nginx 做统一入口。

### 3 分钟版（讲清楚「为什么这么设计」）

1. **背景与痛点**：企业知识散落在 PDF/Word 里，直接问大模型会编；
   单纯向量检索会漏专有名词（工单号、型号），单纯关键词检索不懂同义改写。
2. **我的方案**：
   - 文档流水线：解析（保留页码）→ 结构化分块（带重叠）→ 向量化 → 建 FAISS + BM25 双索引，状态机可观测；
   - 检索：查询改写 + HyDE 扩展召回 → 双路召回 → RRF 融合 → 重排 → 引用溯源；
   - 业务：Spring Boot 做认证/多租户/RBAC/审计，SSE 流式推给 Vue3；
   - 客服：Tool Calling 接订单/工单系统，查不到或置信度低就转人工。
3. **结果**：命中率可量化提升、引用可核查、成本可统计；七个容器一键起。
4. **反思**：小评测集上 BM25 已经很强，混合检索的增益主要在语义型问题上，
   下一步要扩充评测集到 100+ 条并引入答案质量评估。

## 三、高频追问 + 参考回答

### RAG 相关

**Q1：为什么要混合检索？只做向量不行吗？**
> 向量擅长语义（"怎么补办校园卡" ≈ "校园卡丢失处理流程"），但对**专有名词、编号、型号**
> 这类没有语义信息的 token 很弱；BM25 恰好相反。企业场景里工单号 `SO20261016001`、
> 产品型号 `Bud Pro` 这类查询很常见，单路召回必然漏。
> RRF 的好处是**只看名次不看分数量纲**，不用去调「向量分和 BM25 分怎么加权」这个玄学问题。

**Q2：RRF 的公式和 k 值？**
> `score(d) = Σ 1/(k + rank_i(d))`，k 一般取 60。
> k 越大越平滑，排名靠前和靠后的差距被压缩；k 小则更看重头部结果。

**Q3：HyDE 是什么，为什么有用？**
> Hypothetical Document Embeddings：先让模型「编」一段假设性答案，再用这段答案去做向量检索。
> 原理是**问题短、文档长**，直接拿问题去匹配文档，语义空间距离偏大；
> 生成一段「像文档的文本」再去匹配，向量更靠近真实文档。代价是多一次模型调用。

**Q4：引用溯源怎么做到页码级的？**
> 关键在于**解析阶段就把页码保留下来**：PDF 逐页抽文本，每页作为一个 block；
> 拼全文时记录「偏移区间 → 页码」的映射表；分块时用块的起始偏移反查页码。
> 如果一开始就拍平成一个字符串，页码信息就永久丢了，后面再补不回来。

**Q5：分块大小怎么定？**
> 默认 500 字符、重叠 80。太大会稀释语义（一个块里混了多个主题），
> 太小会切断上下文。重叠是为了防止答案正好被切在边界上。
> 我做了**结构化分块**：先按标题/空行/列表项切成语义段，再贪心装箱，比定长硬切效果好。

**Q6：你的向量检索 Hit@1 只有 50%，是不是实现有问题？**
> （★ 这题一定会被问，别慌，这里最能体现你懂不懂）
> 第一，那是**离线 Mock 向量**（词哈希），本来就不具备真正的语义能力，只有词面重叠信号；
> 第二，50% → 87.5% 恰好证明了**单路召回不够**这个论点。
> 第三，我不会为了好看去调参刷指标：**评测集只有 8 条，动一个参数就能翻转 12.5 个百分点**，
> 那是过拟合。真正该做的是把评测集扩到 100+ 条，并引入答案质量评估。
> 第四，RAG 真正关心的是 **Hit@K** —— 答案进了 Top-K 就能回答，Hit@3/@5 都是 100%。

**Q6.5：既然 BM25 单独就是 100%，你为什么还要做混合检索和重排？**
> （这是最尖锐的追问，一定要接得住）
> 因为**这个语料太小了**（11 个分块），词面重叠信号压倒性地充足，语义检索没有发挥空间。
> 混合检索的价值在两种情况下才显现：
> 一是语料变大、同一概念有多种表述（用户说「补卡」，文档写「校园卡补办」）；
> 二是问题口语化、含错别字或同义改写——向量能兜住，BM25 兜不住。
> 我保留混合架构是因为它**在真实规模下更稳**，而不是因为它在 8 条样本上更好看。

### 工程与架构

**Q7：为什么拆成 Java + Python 两个服务，不用一个语言写完？**
> Java 侧的企业能力（Spring Security 的 RBAC、JPA 事务、多租户、审计）成熟且好维护；
> Python 侧的 AI 生态（FAISS、LangChain、pypdf、python-docx）最全。
> 硬用一种语言，要么 Java 侧调 AI 库很别扭，要么 Python 侧做企业级权限很痛苦。
> 拆分后职责单一，也能各自独立扩容——检索是 CPU 密集，业务是 IO 密集。

**Q8：多租户怎么隔离的？**
> 所有业务表都带 `tenant_id`，JWT 里携带租户信息，过滤器解析后写入 `TenantContext`（ThreadLocal），
> 数据访问层统一拼接租户条件。租户之间数据不可见，管理员也只能看到自己租户的数据。
> （进阶答法：数据量大可以升级成「分库分表」或「行级安全策略 RLS」。）

**Q9：SSE 和 WebSocket 怎么选？**
> 这个场景是**服务端单向推送**（模型吐字），SSE 足够且更轻：基于 HTTP、自带断线重连、
> 不需要额外协议升级。WebSocket 适合双向高频通信（比如协同编辑）。
> 实现上后端用 Spring 的 `SseEmitter`，Nginx 侧必须关缓冲，否则会变成「憋到最后一次性返回」。

**Q10：文件上传的文档怎么存的？**
> 原始文件进 MinIO（对象存储），元数据进 MySQL（`kb_document.file_key` 指向对象键），
> 解析后的分块进 `kb_chunk`。本地开发没有 MinIO 时，`app.storage.type=local` 会切到本地目录实现，
> 接口不变——这是**策略模式 + 配置切换**，Docker 里切回 MinIO。

**Q11：成本统计怎么做的？**
> 每次模型调用（对话/向量化/重排/改写）都写一条 `ai_call_log`，
> 记录 provider、model、prompt_tokens、completion_tokens、按单价折算的 `cost_yuan` 和耗时。
> 这样能按租户、按模型、按日期出成本报表，也能给租户设置 token 配额。

**Q12：异步解析怎么实现的？为什么不用 MQ？**
> 当前是 Spring 的 `@Async` 线程池 + MySQL 状态机，前端轮询状态。
> 单机中小规模够用且简单；要支持多实例、断点重试，就该换 RocketMQ/Kafka，
> 这一步我在 README 的「待完善」里列了。

### 部署

**Q13：Docker Compose 里怎么保证启动顺序？**
> 用 `healthcheck` + `depends_on: condition: service_healthy`。
> 只写 `depends_on` 只能保证「容器起来了」，不能保证「服务能用了」——
> MySQL 初始化要几十秒，后端先起来就会连不上库。

**Q14：镜像怎么优化的？**
> 后端和前端都用**多阶段构建**：构建阶段带 Maven/Node，运行阶段只留 JRE/Nginx，
> 镜像体积能小一半以上。后端还先只拷 `pom.xml` 跑 `dependency:go-offline`，
> 利用层缓存，改代码不用重新下依赖。

## 五点五、四个真实排查案例（面试最值钱的素材）

面试官问「你遇到过最难查的 bug」时，用这四个。它们的共同点是：**不报错，只是结果不对**——
这类问题最考验功底，也最能体现你在真实项目里干过。

### 案例 1：JPQL 多列查询 + 裸 `Object[]` 被双重包装，成本报表恒为 0

**现象**：`/api/admin/cost` 永远返回 `totalTokens=0, totalCost=0, totalCalls=0`，但接口 HTTP 200、不报错。

**排查**：先直接查库 —— `ai_call_log` 里明明有 7 条记录（322 tokens / ￥0.000628）。
再用和代码里完全相同的 WHERE 条件跑原生 SQL，结果也对。
**说明 SQL 语义和租户上下文都没问题，bug 在 JPA 映射层。**

**根因**：
```java
@Query("select coalesce(sum(l.totalTokens),0), coalesce(sum(l.costYuan),0), count(l) from ...")
Object[] summary(...);          // ← 返回类型声明成裸 Object[]
```
Spring Data 把单行多列结果**双重包装**成 `Object[]{ Object[]{322, 0.000628, 7} }`，
于是守卫条件 `summary.length >= 3` 不成立（实际是 1），**静默地保持 0**。

**修法**：改成原生查询 + `List<Object[]>`（与另外三个已能工作的分组查询风格统一），
并加 `log.warn` 打印实际列数——**关键教训是「不要静默吞掉异常分支」**。

**能讲出来的点**：为什么裸 `Object[]` 和 `List<Object[]>` 行为不同；
以及「接口成功但数据不对」比「抛异常」危险得多，所以验收断言必须写成
「有真实数据」而不是「接口没报错」——我把这条断言从 `code==0` 加严成了 `totalCalls>0 && totalTokens>0`。

### 案例 2：SSE 跨线程丢了 ThreadLocal 租户上下文

**现象**：流式对话接口偶发 500，报 `当前请求没有租户上下文`。

**根因**：多租户用 `TenantContext`（ThreadLocal）实现，而 SSE 是在**另一个线程池**里推送的，
新线程拿不到请求线程的 ThreadLocal。

**修法**：在**请求线程**里把 `CurrentUser` 取出来，显式传给异步任务（`runWithTenant(...)`），
执行完在 `finally` 里清理——**不清理会在下次复用该线程时串租户**，那是数据越权。

**能讲出来的点**：ThreadLocal + 线程池 = 必须手动传递与清理；
以及「跨线程丢上下文」是多租户系统的经典坑。

### 案例 3：`@Async` 自调用失效，异步上传其实在同步阻塞

**现象**：文档上传接口耗时很长，但功能看起来正常，所以一直没发现。

**根因**：`DocumentService.upload()` 内部直接调 `this.processAsync()`，
**不经过 Spring 代理**，`@Async` 完全不生效。而且当时租户上下文"碰巧"可用，掩盖了问题。

**修法**：把异步方法抽到独立 Bean `DocumentProcessService`，跨 Bean 调用才走代理。

**能讲出来的点**：Spring AOP 是基于代理的，自调用天然失效；
同类问题还有 `@Transactional`、`@Cacheable`、`@PreAuthorize`。

### 案例 4：`@Modifying` JPQL 删除缺事务，文档直接 FAILED

**现象**：重建索引时文档状态直接变 `FAILED`，报 `TransactionRequiredException: Executing an update/delete query`。

**根因**：`@Modifying` 的 JPQL 更新/删除**必须**在事务里执行。

**修法**：新增 `@Transactional(REQUIRES_NEW) replaceChunks()`，
并用 self-injection（`ObjectProvider<DocumentProcessService>`）调用自身代理保证切面生效；
同时保证「删旧 + 插新」原子，不会出现没有分块的中间态。

**能讲出来的点**：`REQUIRES_NEW` 与默认 `REQUIRED` 的区别；
以及为什么「重建索引」这种操作需要独立事务（失败不该污染外层）。

> **这四个案例的通用价值**：它们都不是"写错语法"，而是**框架机制理解不到位**导致的静默错误。
> 讲这类问题，比讲"我用了什么框架"更能证明你懂原理。

## 六、这份简历的「护城河」在哪

大多数简历上写 RAG 的人是：调 LangChain 的 `VectorStoreRetriever` + 调 OpenAI 接口。

你能讲出**别人讲不出的东西**：

1. **RRF 为什么比加权求和稳健**（名次融合 vs 分数量纲）
2. **引用溯源必须在解析阶段就保留页码**，否则补不回来
3. **FAISS 在 Windows 中文路径会失败**（底层 C++ 用 ANSI fopen）
4. **SSE 反代三件套**：`proxy_buffering off` + `proxy_cache off` + 超时拉长
5. **自己的评测集和指标**，敢报「50% → 87.5% / Hit@5 100%」，
   并且能解释**为什么不去调参把它刷成 100%**（过拟合 8 条样本）——
   这种「知道指标的局限」比报一个漂亮数字可信得多
6. **降级设计**：没有 Key / 没有 Redis / 没有 MinIO / 没有 Docker，都能跑
7. **改分块跨页问题**：为了让引用页码精确，把分块改成不跨页，
   代价是跨小节问题单块命中率下降——**能主动说出自己方案的代价**，是高级工程师的标志

第 5、6、7 条最能体现工程成熟度——**能说清楚「我的东西在什么条件下会失效」**，
比一味吹「效果很好」可信得多。
